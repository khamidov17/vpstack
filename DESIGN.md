# Design: vpstack — VP2026 Voice-Privacy Toolkit for AI Coding Agents

Generated by /office-hours on 2026-04-27
Status: APPROVED
Mode: Builder (open-source / research infrastructure)

---

## Problem Statement

AI coding agents (Claude Code, Codex, Cursor, Claude Desktop) are getting good at executing code tasks but have **no domain knowledge** about voice anonymization or the VP2026 challenge. They don't know:

- What EER, WER, and linkability mean in this context
- What the canonical B1 (McAdams) and B2 (neural) baselines are
- That HuBERT layer 6 matters more than layer 12 for content/speaker disentanglement
- How to set up reproducible eval splits, seeds, and checkpoints
- How to compare anonymized speech against the official VP2026 protocol

Researchers in the VP2026 community currently solve this by hand: copy-pasting baseline configs, running eval scripts manually, tracking experiments in scattered notebooks. Every researcher rebuilds the same plumbing. AI agents compound the problem by hallucinating SpeechBrain conventions and inventing baseline numbers.

vpstack closes that gap with a domain-specific toolkit that auto-activates on voice-anonymization projects and stays completely silent everywhere else.

## v0.2 Architecture (2026-04-29)

**The MCP server was deleted in v0.2.** Any reference to vp_run_baseline, vp_run_eval, vp_run_attacker, vp_check_submission, or any other MCP tool below this notice is historical documentation of a design that no longer exists. The v0.2 architecture is:

- **Skills:** 15 SKILL.md files that tell Claude what bash commands to run
- **State:** Written to `~/.vpstack/projects/{slug}/` via Claude's Write tool directly
- **Computation:** B1 McAdams script generated to `/tmp/vp_b1_run.py` by Claude on demand; attacker and B2 reference the official VP2026 challenge scripts
- **No Python code in the repo.** No MCP server. No pip install beyond what the researcher already needs.

This follows the gstack pattern: markdown skills + bash = Claude Code, Codex, Cursor all work identically with zero additional setup.

---

## What Makes This Work

1. **Domain knowledge encoded where Claude reads it.** `docs/domain.md` gives Claude the VP2026 facts (metric directions, component tradeoffs, known pitfalls) so it stops hallucinating baseline numbers.
2. **Cross-tool by design.** Skills work in Claude Code, Codex (AGENTS.md), and Cursor without any MCP config — just bash.
3. **Silent on unrelated projects.** Auto-activation fires only on voice-anonymization signals. Completely silent elsewhere.
4. **Self-improving feedback loop.** Opt-in anonymous telemetry. Never sends code or research data.
5. **Dogfooded from day one.** Every skill shaped by real VP2026 research need.

---

## Constraints

1. Audience is small (~100–300 active VP2026 researchers). Optimize for **value per user**, not adoption velocity.
2. **Correctness > coverage.** A wrong baseline number propagates to citations. The bar is higher than mass-market dev tools, not lower.
3. Must work without GPU on laptop dev (skills run via bash); GPU only for actual recipe execution.
4. Must respect researcher privacy — telemetry never sends code, file paths, hypothesis text, eval numbers, or repo names.
5. Must auto-activate ONLY on voice-anonymization projects, silent everywhere else.
6. **VP2026 specifically.** All metric references, baseline specs, and attacker conditions follow the VP2026 Eval Plan PDF. Do not reference VP2022, VP2020, or VP2024 numbers as current targets.

### The 6 Skills (v0.1)

Each follows the gstack pattern: YAML frontmatter, preamble (activation check + version check + telemetry start), workflow body, telemetry end.

| Skill | Purpose | Calls into MCP |
|---|---|---|
| `/vp-hypothesis` | Formalize what an experiment tests (hypothesis, expected delta, evaluation criteria). Writes `~/.vpstack/projects/{slug}/hypotheses/{id}.md`. | `vp_get_component_info` |
| `/vp-spike` | Run 1–3 focused ablations with given/when/then verdicts. Writes `~/.vpstack/projects/{slug}/spikes/{id}.md`. | `vp_run_baseline`, `vp_run_eval`, `vp_log_experiment` |
| `/vp-baseline-compare` | Run B1/B2 + user system, return delta table (EER/WER/linkability). | `vp_run_baseline`, `vp_run_eval` |
| `/vp-eval` | Full VP2026 eval pipeline. Validates submission format. | `vp_run_eval`, `vp_check_submission` |
| `/vp-repro-check` | Verify seeds, splits, checkpoints. Returns PASS/FAIL with specific reason. Catches silent drift. **Limitation:** does NOT track vpstack version — if recipe code changes between experiments, repro-check passes formally but observed numbers may differ. Researchers responsible for noting vpstack version in their lab notebooks. | `vp_check_reproducibility` |
| `/vp-writeup` | Generate **internal experiment report** (what was done, method, hyperparameters, results table, config hash) from `~/.vpstack/projects/{slug}/` logs. **Does NOT generate citations or research-paper prose** — that's the researcher's job. Output is a structured engineering log, not a manuscript section. | `vp_search_experiments` |

**Artifact location split (gstack pattern):**
- **Repo-local `<repo>/.vpstack/`** — activation markers (`enabled`, `disabled`) only. Tiny, project-local. User can gitignore or commit.
- **User-level `~/.vpstack/projects/{slug}/`** — all research artifacts (hypotheses, spikes, experiment outputs). Per-project subdirectory, slug derived from repo basename. Mirrors `~/.gstack/projects/{slug}/`.
- **User-level `~/.vpstack/config.json`** — telemetry mode, activation_override, version cache. Mirrors `~/.gstack/config`.

### MCP Server Tool Signatures

```python
vp_run_baseline(baseline: Literal["B1", "B2"], data_path: str, seed: int = 42)
  → {"eer": float, "wer": float, "linkability": float, "config_hash": str}

vp_run_eval(system_path: str, eval_set: Literal["dev", "test"], seed: int = 42)
  → {"eer": ..., "wer": ..., "linkability": ..., "side_channels": {...}}

vp_check_submission(submission_path: str)
  → {"valid": bool, "errors": List[str], "warnings": List[str]}

vp_check_reproducibility(config_path: str)
  → {"status": "PASS"|"FAIL", "reason": str, "missing": List[str]}

vp_get_component_info(component_name: str)
  → {"description": str, "tradeoffs": Dict, "papers": List[str]}

vp_search_experiments(query: str, limit: int = 10)
  → {"matches": [{"id": str, "summary": str, "eer": float, ...}]}

vp_log_experiment(exp_id: str, metrics: Dict, config_hash: str)
  → {"logged": bool, "path": str}
```

### Auto-activation mechanism (the critical design)

**Hybrid: heuristic detection + explicit override + first-run confirmation.**

Each skill's preamble runs:

```bash
ACTIVATION=$(vpstack-detect 2>/dev/null)
case "$ACTIVATION" in
  ENABLED_EXPLICIT) ;;            # .vpstack/enabled present — proceed
  DISABLED_EXPLICIT) exit 0 ;;    # .vpstack/disabled present — silent exit
  DETECTED_FIRST_RUN) ;;          # heuristic match, never asked here before — prompt user once
  DETECTED_CONFIRMED) ;;          # heuristic match, user said yes previously — proceed
  NO_MATCH) exit 0 ;;             # nothing voice-related — silent exit
esac
```

**Detection signals (any one triggers DETECTED_*):**
1. `.vpstack/` directory exists in CWD or any parent
2. `vp_config.yaml` file exists in project root
3. `speechbrain` listed in `requirements.txt`, `pyproject.toml`, or `environment.yml` (any speechbrain project — first-run prompt lets user disable if not voice-related; prevents false-negatives on repos named `phd/`, `experiments/`, etc.)
4. CLAUDE.md or README.md in project root contains "VP2026" or "voice anonymization" (case-insensitive)
5. Path matches `*VP2026*`, `*voice-anon*`, or `*voice-privacy*`

**Headless mode (CI / no-TTY):** `--headless` flag on any skill bypasses the first-run prompt and treats `DETECTED_FIRST_RUN` as `DISABLED_EXPLICIT`. Required for skills running in non-interactive environments (CI, pipes, automation). Without this, skills would hang waiting on input.

**First-run flow per project (DETECTED_FIRST_RUN):**

> "This project looks like voice-anonymization work (matched: speechbrain dependency + 'voice' in repo name). Enable vpstack here?"
> A) Yes, enable (writes `.vpstack/enabled`)
> B) No, silence vpstack on this project forever (writes `.vpstack/disabled`)
> C) Ask me again next time

The user is in control. False positives cost one click. False negatives cost one `/vp-init` call.

### Auto-update flow

`vpstack-update-check` runs in every skill preamble. Pings `https://vpstack.dev/api/version` (HTTP HEAD with 1s timeout, cached for 6 hours). On version mismatch, prints `UPGRADE_AVAILABLE 0.1.0 0.2.0`. Skill notices and runs the upgrade flow:

> "vpstack 0.2.0 available (you're on 0.1.0). Upgrade now?"
> A) Yes, upgrade (runs `npx vpstack@latest --upgrade`)
> B) Show changelog first
> C) Skip this version
> D) Don't ask again until next minor

User always confirms. No silent auto-update. Network failure = silent skip; never blocks the workflow.

### Telemetry design

**Three modes, presented at install:**

| Mode | What gets sent | What it enables |
|---|---|---|
| `off` | Nothing. Zero network calls. | Maximum privacy. |
| `anonymous` | Skill name + duration + outcome. No device ID, no session linkage. Just an aggregate counter. | Knowing if anyone is using vpstack at all. |
| `community` | Anonymous fields + stable device ID (hash of machine UUID + user) + vpstack version + skill name + duration + outcome (success/error/abort) + error class (no message text). | Trend tracking across versions, finding broken skills, fixing bugs faster. |

**Never sent (in any mode):**
- Code, file contents, file paths
- Hypothesis text, experiment IDs, eval numbers
- Repo names, branch names, project paths
- User-typed prompts or any natural-language content
- Hyperparameters, seeds, config hashes

**Install flow presents all three options explicitly.** No dark pattern. "No thanks, fully off" is a real choice on the first screen, not buried.

```
$ npx vpstack@latest
…
[Telemetry] vpstack improves faster when we know which skills break.
  A) Help vpstack get better — community mode (recommended)
  B) Anonymous mode — just a counter, no device ID
  C) No thanks, fully off
```

Config persists at `~/.vpstack/config.json`. Changeable any time with `vpstack-config set telemetry off`.

Three packages, one repo, one release cadence. Users install whichever subset they need.

## v0.1 Explicit Non-Goals (out of scope)

These are conscious cuts from v0.1, captured so they don't silently re-enter scope:

- **No SLURM / async job model.** v0.1 assumes researcher runs MCP locally on laptop or SSH'd-into single-GPU server. `vp_run_baseline` is sync, blocks for hours, streams progress. Async cluster integration deferred to v0.2 if researcher uses a scheduler.
- **No per-project version pinning.** vpstack auto-updates globally (gstack pattern). `/vp-repro-check` validates seeds/splits/checkpoints but NOT vpstack version. Researchers responsible for noting vpstack version in their lab notebook. Stated tradeoff.
- **No citation generation.** `/vp-writeup` produces internal experiment reports (methods, params, numbers). Never citations, never paper prose. Researcher writes the manuscript; vpstack writes the engineering log.
- **No HuggingFace leaderboard, no GitHub Action CI integration, no Aider/Continue/Zed support.** Post-v0.1.
- **No remote MCP server.** Local stdio only. Sharing across machines = post-v0.1.

## Reproducibility Test Tolerance Note

The CG1/CG2 ±0.5% EER tolerance gates are tight given CUDA non-determinism, cuDNN algorithm selection, and mixed-precision rounding. **Implementation note:** before relying on these gates in CI, measure actual run-to-run variance on the target hardware. If observed variance exceeds 0.3%, widen tolerance to ±1.5% and require N≥3 seeds, OR enable PyTorch deterministic mode (`torch.use_deterministic_algorithms(True)`) and accept the speed hit. Decide after first reproducible run, not now.
